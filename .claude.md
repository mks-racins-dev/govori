# Claude/Copilot Agent Instructions for Govori

You are working on the **Govori** project — a speech analysis platform built with React, ASP.NET Core, and PostgreSQL.

## Core Principles

### 1. Be Pragmatic
- ✅ Implement **exactly** what is requested
- ✅ Follow best practices only when they serve the request
- ❌ Don't add unrequested features
- ❌ Don't refactor unrelated code
- ❌ Don't fix pre-existing issues unless tightly coupled to your change

**Example**: If asked to add a button, don't reorganize the component. If asked to fix a bug in function A, don't refactor function B.

### 2. Always Create a Branch for Changes

**Never commit directly to `main`.** Always follow this workflow:

```bash
git checkout -b feature/description  # or fix/, docs/, test/
# ... make changes ...
git add .
git commit -m "type: description"
git push -u origin feature/description
gh pr create --title "Brief title" --body "What this PR does"
```

**Wait for CI to pass** (`build-test` and `docker` jobs must be green) before merge.

### 3. Respect Existing Code
- Preserve existing behavior unless change is requested
- Don't modify code style in unrelated files
- Don't upgrade dependencies unless asked
- Don't remove "dead code" unless it blocks the requested change

### 4. Validate Before Pushing
Run these locally before `git push`:

```bash
cd backend
dotnet build --no-restore -warnaserror
dotnet format --verify-no-changes
dotnet test
```

If all pass ✅, safe to push. If any fail ❌, fix first.

### 5. Commit Message Format
```
type: short description

Optional longer explanation.

Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
```

**Types**: `feat`, `fix`, `docs`, `test`, `chore`, `refactor` (only if requested), `style`

## Workflow for Requested Changes

1. **Clarify** — Ask if the request is ambiguous
2. **Branch** — Create feature branch from `main`
3. **Change** — Implement exactly what's requested
4. **Validate** — Run build/format/test locally
5. **Commit** — Use proper message format
6. **Push** — `git push -u origin <branch>`
7. **PR** — Open pull request via `gh pr create`
8. **Monitor** — Wait for CI checks to pass
9. **Merge** — Only after all checks are green ✅

## Branch Naming

- `feature/user-authentication` — new features
- `fix/login-timeout` — bug fixes
- `docs/api-setup` — documentation
- `test/ci-validation` — testing/validation
- `refactor/database-layer` — refactoring (only if explicitly requested)

## What NOT to Do

| ❌ Don't | ✅ Do Instead |
|---------|-------------|
| Commit directly to `main` | Always use a feature branch |
| Mix multiple concerns in one PR | One feature/fix per PR |
| Update unrelated dependencies | Only update if explicitly requested |
| Refactor large sections | Only refactor the minimum needed |
| Disable tests to pass them | Fix the code to pass the tests |
| Ignore failing CI | Fix all issues before merge |

## Key Rule: Branch Protection on `main`

- ❌ No direct pushes to `main`
- ❌ No merges without PR
- ❌ No merges without passing CI checks
- ✅ All changes go through feature branch → PR → CI → merge

This is enforced by GitHub branch protection rules. If you try to bypass this, the system will reject it.
